4) Two reasons branches are used in a Git repository
----------------------------------------------------
a) Isolation of work: a branch is a separate line of development, so you can
   build a new feature or fix a bug without touching the stable main code.
   Unfinished or experimental work never breaks what everyone else is using.
b) Parallel collaboration: multiple developers (or one developer on several
   tasks) can each work on their own branch at the same time and then merge
   the results, which keeps their changes from colliding.


5) Difference between "git log" and "git status"
------------------------------------------------
git log shows the HISTORY of the repository: the commits already made, with
their hashes, authors, dates, and commit messages.
git status shows the CURRENT STATE of the working directory and staging area
right now: which files are modified, staged, or untracked, and whether your
branch is ahead of or behind the remote.
In short: git log looks at the past (committed history); git status looks at
the present (uncommitted changes).

8) Object-Oriented Programming concepts
---------------------------------------
(I) Inheritance: a mechanism in which one class (the child / derived /
    subclass) acquires the attributes and methods of another class (the
    parent / base / superclass). It lets you reuse code and build specialized
    classes from more general ones. Example: in this repository Car, Bicycle,
    and PoweredVehicle all inherit from the base Vehicle class, getting
    Vehicle's data and behavior while adding their own.

(II) Polymorphism: the ability for the same interface or method call to
    behave differently depending on the actual object type acting on it. In
    C++ this is commonly done with virtual functions: a base-class pointer
    can call an overridden method and the correct derived version runs at run
    time. Example: calling mileageEstimate() or toString() through a Vehicle*
    actually runs the Car, Bicycle, or PoweredVehicle version depending on
    the real object.

(III) Encapsulation: bundling data (attributes) and the methods that operate
    on that data together inside a class, while restricting direct access to
    the internal state (e.g. with private members) and exposing only a
    controlled public interface (e.g. getters/setters). This protects an
    object's data from invalid outside modification and hides implementation
    details.


9) Difference between "Dictator and Lieutenants" and "Integration Manager" workflows
------------------------------------------------------------------------------------
The main difference is the number of integration layers.

In the Integration Manager workflow there is a single integrator. Each
contributor has their own public repository; one integration manager pulls
contributors' changes, tests and merges them, and pushes the result to the
single blessed (reference) repository that everyone else clones from.

The Dictator and Lieutenants workflow adds a hierarchy on top of that idea.
Instead of one integrator there are several "lieutenants," each responsible
for integrating the changes of one subsystem / part of the project. A single
"dictator" then merges the lieutenants' branches into the reference
repository. So it is a multi-tier version of the integration-manager model
(used by very large projects such as the Linux kernel), whereas the
integration-manager workflow has only one integrator.


10) How a team of 100 developers benefits from "Dictator and Lieutenants" over "Centralized"
--------------------------------------------------------------------------------------------
In a Centralized workflow everyone shares and writes to one single
repository. With 100 developers that repository becomes a bottleneck and a
single point of failure: everyone competes to push to the same place,
conflicts are frequent, a single broken commit immediately affects all 100
people, and there is no built-in layer of review or ownership.

The Dictator and Lieutenants workflow scales far better because the
integration work is divided up. Each lieutenant owns and integrates one
subsystem, so the 100 developers are split into manageable groups working in
parallel without stepping on each other. Changes are reviewed and filtered at
the lieutenant level before the dictator merges them into the canonical
repository, which keeps the main history clean and stable. This distributes
the workload, adds quality-control checkpoints at each tier, isolates
mistakes to a subsystem instead of the whole project, and removes the
single-bottleneck problem of the centralized model.
